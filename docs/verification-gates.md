# Verification gates

Demoted verbatim from `AGENTS.md` on 2026-09-05, apart from the Windows corrections noted below. Self-references such as "this file" and "this section" refer to the original.

This project uses the [pre-commit](https://pre-commit.com) framework. Its config (`.pre-commit-config.yaml`) is cloned with the repo; each clone enables the hooks once:

```bash
pre-commit install && pre-commit install --hook-type pre-push
```

`pre-commit` is a Python tool. For non-Python templates, install it with `uv tool install pre-commit` or `pipx install pre-commit`.

## Per-commit checks

On every commit, lightweight hooks run: end-of-file fixer, trailing-whitespace trimming, merge-conflict detection, YAML/TOML validation, mixed-line-ending and case-conflict guards, and `check-added-large-files` — a portable 5 MB size guard that blocks accidentally committing heavy blobs (a big blob bloats `.git` history even after deletion).

## Pre-push verify gate

On `git push`, the `verify` hook runs the project's verify command: `data-raw/check-floor-drift.R --self-test`, then `lintr::lint_package()`, then `spelling::spell_check_package()`, then `scripts/check-docs-drift.R` (man/, NAMESPACE and DESCRIPTION must be what roxygen regenerates from R/, at the pinned roxygen2; added 2026-10-05, `SEOR-nwfmerhu`; it checks the commit being pushed, `PRE_COMMIT_TO_REF` or else `HEAD`, on a `git archive` export in a temporary directory that is removed on every exit, so it never rewrites the working tree and an uncommitted fix or an untracked `.Rd` cannot make it pass; CI's images have no git, so `check:linux-release` runs it on the job's own checkout, which is the commit; the deep-check legs set `NO_DOCS_DRIFT=1`), then `data-raw/check-urls.R` (every declared URL must resolve; added 2026-10-03, `SEOR-lavybtkr`), then `rcmdcheck::rcmdcheck(args = "--as-cran", error_on = "warning")`. Since 2026-08-02 that chain lives in **`data-raw/verify.sh`**, and the hook and `.gitlab-ci.yml` both invoke it — so "the hook runs the same chain as CI" is a fact about one file rather than a coincidence between hand-maintained copies that was about to become three (`RADD-fgciezpx`). The one deliberate difference is a `NO_MANUAL` knob: CI images carry no LaTeX toolchain and pass `--no-manual`, the hook does not, and `docs/ci-workflow-lint.md` is where that asymmetry was examined and found correct. Server-side branch protection was unavailable on the GitHub plan, which is why this local pre-push gate was built as the stand-in for it. It is no longer the only layer: since 2026-08-01 `main` is a protected branch on the GitLab remote — `allow_force_push=false`, push and merge restricted to Maintainers — so the guarantee the hook was approximating now also exists server-side, on the remote actually being pushed to. Since 2026-08-02 the release **tags** are protected too, `v*` with creation restricted to Maintainers, which closes the asymmetry that had `main` guarded while `v0.1.1` — by then the only thing claiming that version number (`RADD-xuqkzgdl`) — could still be moved or deleted by a push. The two are not redundant. Protection rejects a bad *push*; it has no opinion about whether the tree passes `--as-cran`.

**A third layer used to hold exactly that opinion, and it has been narrowed twice, then removed as a possibility at all.** As set on 2026-08-02 (`RADD-vvdpvysm`) the project carried `only_allow_merge_if_pipeline_succeeds=true` with `allow_merge_on_skipped_pipeline=false`, so a merge request could not merge until its pipeline passed — demonstrated by MRs !17 and !18, both of which sat unmerged until they went green. That setting drifted between `true` and `false` several times afterward (`RADD-jzwticug`, `RADD-dyqdamzt`), including a same-day deadlock where MR !46 got `detailed_merge_status: ci_must_pass` against a `head_pipeline: null` it could never produce. It was set to `false` again on 2026-09-22 (`RADD-dyqdamzt`) and now has to stay off for a stronger reason than before: since `SEOR-bmgkzhvy` **no merge request creates a pipeline at all**, DESCRIPTION-changing or not, and GitLab blocks a merge when that setting is on and no pipeline exists — the exact failure mode MR !27 and MR !46 both hit, and a documented GitLab troubleshooting case rather than a local surprise.

So state the current shape without softening it: **the remote no longer gates a merge.** A version-bump pipeline is evidence a reviewer can read, not enforcement. What actually refuses a bad tree is the pre-push hook, and the only reason that is tolerable is that `data-raw/verify.sh` is the same chain — an ordinary MR loses the clean clone and the clean library, not the checks.

What server-side protection remains is about **pushes**, not about check results. `main` is protected and `v*` tags are protected; `dev` is not, so a direct push to `dev` still reaches it without an MR and is checked by the local hook alone. Nothing prevents that, and it is how `dev` was advanced before merge requests existed on this remote. Since the merge gate came off, that route and the merge-request route are checked by the same thing — the pre-push hook — which makes the distinction between them smaller than it was, not larger.

**CI now runs.** `.gitlab-ci.yml` was added on 2026-08-02 and went green the same day: two jobs on GitLab's shared **native** amd64 runners, `check:linux-release` (R 4.6.1, p3m binaries) and `check:linux-devel` (R-devel r90334, source builds), both reporting **`Status: 1 NOTE`** — the `--as-cran` incoming note and nothing else. **That is no longer where it runs.** The namespace's SaaS compute quota ran out; the last amd64 pipeline ran on 2026-09-06, and since 2026-09-10 every job runs on `seor-local-docker`, a self-hosted Docker runner on an arm64 Mac, so both check jobs are Linux **aarch64** today (`SEOR-auklpuoa`). `docs/gitlab-ci.md` is the transcript of that first run (`RADD-fgciezpx`) and describes the trigger rules as they stood that day; it is a transcript and is not updated to match later states. The rules have moved twice since. From `RADD-ofvmkjsj` (2026-08-02) it ran on **version bumps only** — a merge request that changed `DESCRIPTION`, and a `v*` tag — rather than on every merge request. Since `SEOR-bmgkzhvy` (2026-09-22) it runs on **a push to `main`, a `v*` tag, or a pipeline someone starts by hand** — no merge request creates a pipeline at all any more, DESCRIPTION-changing or not, because a merge request pipeline was found to outlive its own merge and stall the fleet's one self-hosted runner behind pipelines re-verifying trees that no longer existed. The hand-started case was added on 2026-09-23 and is what makes a pre-merge clean-room check possible again: open **Build > Pipelines > Run pipeline**, pick the branch, and both check jobs run against it. It must be the button — `glab ci run` starts an `api`-source pipeline, which is still refused on a branch. `.gitlab-ci.yml`'s `workflow:` block is where both changes are argued in detail, including what each one costs. `check:linux-devel` lost its `when: manual` override in the first change, so a green pipeline is two-platform evidence, and it ran on every merge to `main` rather than only near a release until 2026-10-03, when it became the `deep-check:devel` leg of the weekly schedule (`SEOR-lavybtkr`). The sentence this paragraph used to carry — that the local hook "is not a stand-in for CI, it is the only gate there is" — is retired, and it was retired by evidence rather than by intent: the first pipeline **failed**, on a missing `libcurl4-openssl-dev` that no local row could have found, because `rcmdcheck` imports `curl` and `data-raw/check-matrix.sh` calls `R CMD check` directly and so never installs `rcmdcheck` at all.

Two jobs, not six rows, is deliberate — six being the matrix the since-deleted GitHub workflow declared. Five of those six are already answered by measurements in `docs/`; what CI adds is the four things a laptop cannot assert about itself — a clean clone, a clean package library, native amd64, and a result tied to a commit. Since 2026-09-10 it asserts three of them: the runner is arm64, so CI no longer asserts native amd64, and since 2026-09-24 it is decided that it will not (`SEOR-auklpuoa`; see *Linux amd64 is checked at release, not in CI* below). Those four are now asserted **once per version bump** rather than once per merge request, which is a real reduction and a deliberate one: they matter about the artifact a user installs, and a merge request that leaves `DESCRIPTION` alone is not producing one. It does **not** add Windows (checked by no automated gate — `docs/win-builder.md` records the one manual win-builder run, `RADD-xxuzwmuj`), macOS beyond the hook (a self-hosted Mac runner *for macOS* is *rejected*, not pending; the Mac runner CI does use executes Linux containers), minimum dependency versions, or any semantic diversity the libc oracles do not already provide.

**GitHub is gone from this tree, and it was not taken away — it was given up.** `.github/workflows/R-CMD-check.yaml` was deleted on 2026-09-05, along with the `github` git remote and the `^\.github$` line in `.Rbuildignore` (`RADD-ithxwzpr`). The workflow declared six matrix rows and **never executed once** in its entire life: the account hosting the repository has been suspended since 2026-07-20, support stopped responding, and GitLab does not read `.github/`. Keeping the file meant keeping a description of a capability the project did not have, which is the same failure mode as an unversioned `Imports:` entry — an assertion nothing checks. Nothing was changed on GitHub's side; the account is suspended and whatever sits there is untouched. This was a change to what *this tree* waits on.

Two things survive the deletion, and neither is an argument for having kept it. `docs/ci-workflow-lint.md` remains the transcript of linting that workflow (`RADD-ushiurrv`) — actionlint 1.7.12 clean, plus the three judgment calls actionlint cannot make, each resolved against the `r-lib/actions` sources and found correct: an `http-user-agent` key on the r-devel row only, `needs: lint` against a DESCRIPTION carrying no `Config/Needs` field, and `--no-manual` in CI but not in the hook. And `data-raw/verify.sh` is the shape that keeps a migration back cheap: a provider installs an environment and calls one script.

**Do not sweep the remaining `github.com` strings out of the tree.** After the deletion they are all one of two things, and both must stay. Third-party provenance: `inst/COPYRIGHTS`, `data-raw/wpt-provenance.dcf` and `data-raw/vendor-wpt.R` cite web-platform-tests, `docs/upstream-reports/*` cite python/cpython, and `.pre-commit-config.yaml` cites pre-commit-hooks — `inst/COPYRIGHTS` in particular is the licensing attribution a CRAN reviewer reads. And transcripts under `docs/`, which record what was true when they were written; editing one to match a later state is what stops it being a transcript.

## Citation metadata names the release

Since 2026-09-12 a fourth check runs on the same pre-push hook and in the pipeline: `scripts/check-citation.py`, ported verbatim from seor (`SEOR-jxzjhbef`). It asserts two things about `CITATION.cff` and `.zenodo.json` — that each names **the release `DESCRIPTION`'s `Version` points at** (`X.Y.Z` stays `X.Y.Z`; `X.Y.Z.9000` drops to `X.Y.Z`, with a never-released package carrying its development version verbatim and no `date-released` and no DOI), and that every `http(s)` URL either file declares also appears in `DESCRIPTION`'s `URL:` field. The reasoning is seor's `design/adr/0001-citation-metadata-names-the-release.md` and `0002-citation-urls-are-the-ones-about-this-package.md`. The practical consequence is a release-order one: **both files move at the `DESCRIPTION` bump that opens a release cycle, not at the tag** — they are part of the release rather than a record of it.

**raddr carries both files since `RADD-dxzfcbjx`.** Until then it carried neither, and whether it should was left open (`SEOR-lreejxat` item 4). What settled it: Zenodo is on for the GitHub mirror, so the next GitHub Release mints a permanent DOI either way, and without `.zenodo.json` Zenodo builds that record from metadata it scrapes. Both files name 0.1.2, the release `0.1.2.9000` descends from, with `date-released` the day CRAN published it (2026-09-21). They carry no DOI, because no deposit exists yet. `CITATION.cff` has no `repository:` pointing at the CRAN page either: `DESCRIPTION`'s `URL:` does not list that page, and the check would refuse it. The check is offline, stdlib-only and instant — the `citation-version` job runs on `python:3.13-alpine` with no R image, no `.r-job` and no cache, which is why it costs seconds on runner slots the whole fleet shares on one Mac, where the two check jobs are long. It inherits the `workflow:` rules rather than carrying its own; since `SEOR-bmgkzhvy` that means it now runs on every push to `main`, every `v*` tag and every hand-started pipeline, more often than the moment it actually cares about (both files move at the `DESCRIPTION` bump, not at every merge), but at seconds a run that costs nothing worth carving a narrower rule for.

**After the tag, archive the release on Zenodo and record its version DOI** (fleet release checklist, seor `design/release-checklist.md`, `SEOR-ygfaewuo`). Zenodo deposits on a GitHub Release on the read-only mirror, not on the tag, so a tag alone deposits nothing. Skip this and `CITATION.cff` keeps naming the previous version's DOI, or none. raddr's next release is its first through this step, so it creates the first archive.

1. **Owner, first archive only.** Check that the repository is ON in Zenodo's GitHub settings, which adds a `release` webhook to the mirror.
2. **Agent.** Check that the tag object matches on both forges: `git ls-remote --tags origin 'refs/tags/vX.Y.Z'`, then the same against `https://github.com/bart-turczynski/raddr.git`.
3. **Owner.** Create the GitHub Release from that tag, never letting GitHub create one: `gh release create vX.Y.Z --verify-tag -R bart-turczynski/raddr`.
4. **Agent.** Wait for the record. It usually takes minutes, and a release at "Received" on Zenodo's GitHub page can take well over an hour. Wait at least two hours before emailing support. Never re-create the release without the owner's approval: it makes a duplicate version.
5. **Agent.** Check the record's version and title against the release. Zenodo reads both from `.zenodo.json` in the tagged archive, not from `DESCRIPTION` or the tag name: `curl -s 'https://zenodo.org/api/records?q=conceptrecid:<concept-recid>&allversions=true' | jq '.hits.hits[].metadata | [.version, .title]'`. A wrong version means the tag's `.zenodo.json` was stale; the owner corrects it with a metadata edit on zenodo.org, not a new release. Compare the archived zip with the tag by content, not checksum.
6. **Agent.** Check that doi.org resolves both the concept DOI and the new version DOI: `curl -s -o /dev/null -w '%{http_code}\n' https://doi.org/<doi>` prints `302`. A `404` means DataCite has not registered it yet: wait, and don't commit it.
7. **Agent.** In a follow-up commit, set the version-DOI entry in `CITATION.cff` `identifiers:` (value and description) and `date-released` to this release. On the first archive, also add `doi:` with the concept DOI and its own `identifiers:` entry. `python3 scripts/check-citation.py` must still pass.

A release that stalls at "Received", a duplicate version, and the content comparison are all covered in seor's `design/github-mirror.md` §5 (§5.1 to §5.3).

## Linux amd64 is checked at release, not in CI

**CI itself no longer covers amd64.** Since 2026-09-10 both check jobs run in Linux aarch64 containers on the self-hosted arm64 Mac, and on 2026-09-24 the owner decided not to restore native amd64 to CI (`SEOR-auklpuoa`, option 3). The pre-push hook is arm64 too, and `data-raw/check-matrix.sh` reaches amd64 only under emulation. So between releases nothing checks raddr on native amd64.

The check moves to release time instead. **Before every CRAN release**, as a release-checklist step:

1. Build the tarball from a clean `git archive` export of the release commit (a worktree build adds a hidden-files NOTE; `docs/win-builder.md`, 0.1.2).
2. Submit it to R-hub's R Consortium runners, which need no GitHub account of ours: once per machine `rhub::rc_new_token()` for the maintainer's address, then `rhub::rc_submit("raddr_X.Y.Z.tar.gz", platforms = c("ubuntu-release", "ubuntu-clang"), confirmation = TRUE)`. Both names come from `rhub::rhub_platforms()` in rhub 2.0.1, whose aliases put them on x86_64: `ubuntu-release` is `r-release-linux-x86_64` (R release, Ubuntu 24.04) and `ubuntu-clang` is `r-devel-linux-x86_64-debian-clang` (R-devel). They mirror CI's release/devel pair. Re-list the platforms at release time; if either name is gone, pick the current x86_64 Linux release and devel entries and say so.
3. Record the result as rows under *Test environments* in that release's `cran-comments.md`: platform string from the check header, R version, status, and the run URL. A row counts only if its header says `x86_64-pc-linux-gnu`.

Tracker notes from the GitHub suspension say R-hub v2 is blocked. That was about `rhub::rhub_check()`, which runs in the package's own GitHub repository. `rc_submit()` does not use one.

## Dependency floors are re-measured at release

Since 2026-10-03 the R floor is `R (>= 4.1.0)`, set by the fleet rule (the oldest R minor the fleet's arm64 CI can test) and checked weekly by the `deep-check:floor` job on R 4.1.3; `data-raw/check-floor-drift.R` keeps it equal to that job's image (`SEOR-lavybtkr`). The transcripts below were taken on R 4.0.0 and still carry the Imports floors. The declared floors (`R (>= 4.0.0)` when measured, `vctrs (>= 0.7.0)`, `rlang (>= 1.1.7)`) are measured by `data-raw/check-r-floor.sh` and `data-raw/check-dep-floor.sh`, with transcripts `docs/r-floor-check.md` and `docs/dep-floor-check.md`. Four triggers call for re-running both scripts and refreshing both transcripts (`RADD-olitgnsw`). Two are file state, and `data-raw/check-floor-drift.R` gates them in `data-raw/verify.sh`, so the pre-push hook and CI carry it: a floor raised in `DESCRIPTION`, and a new `Imports:` entry. The other two need the network or a person, so they are a release-checklist step. **Before every CRAN release after the first:**

1. Check whether any `Imports:` dependency, at its current CRAN version, now requires a newer R than the declared floor: `tools::package_dependencies()` on the CRAN package db, or its `Depends` field, for `rlang`, `vctrs` and their closure. A dependency release that drops R 4.0.0 makes the declared floor unreachable in practice without changing a byte of this repository (trigger 3).
2. Re-run `sh data-raw/check-r-floor.sh > docs/r-floor-check.md` and `sh data-raw/check-dep-floor.sh > docs/dep-floor-check.md` when step 1 found one, and at every resubmission, since the dependency closure will have moved (trigger 4). Both need Docker. Commit the refreshed transcripts; `data-raw/check-floor-drift.R` then confirms they match `DESCRIPTION`.

Two cautions travel with a re-run. `check-dep-floor.sh` moves R and vctrs to their floors together, so a failure does not attribute to either alone; its header's `BASE=` fallback (for example `BASE=rocker/r-ver:4.4.2`) separates them. And its equality assert is load-bearing: it installs vctrs at exactly the floor, not `>=`, because a `>=` assert once let a gap stand while an earlier script installed a newer vctrs and looked like a measurement. Don't relax it.

Don't re-run the scripts when no trigger fired. A green re-run against an unchanged premise is not evidence.

## Dependency vulnerability audit

**Reversed 2026-10-03 for fleet alignment (`SEOR-lavybtkr`):** raddr now runs `osv-audit` and `security-audit` on the `dependency-audit` schedule, in seor's shape, with oysteR and rosv in `Suggests:`. The paragraph below records the exemption as it stood.

Some fleet packages run a dependency vulnerability audit: `tests/testthat/test-security.R` against OSS Index via oysteR, `test-osv.R` against OSV via rosv, and scheduled `security-audit` and `osv-audit` CI jobs. raddr has none of these, and that is a decision, not an omission (owner, 2026-09-24, confirmed 2026-09-27; `RADD-hmvlwcyi`, `SEOR-fftbjnpl`). Its direct imports are rlang and vctrs; the full hard-dependency closure, measured 2026-09-27 with `tools::package_dependencies(c("rlang", "vctrs"), which = c("Depends", "Imports", "LinkingTo"), recursive = TRUE)`, is five r-lib packages: cli, glue, lifecycle, rlang and vctrs. None of them reaches the network or links a system library such as curl or OpenSSL, which is where the only advisories found anywhere in the fleet came from. The cost of an audit is adding oysteR or rosv to `Suggests:` of a package already on CRAN, or keeping a CI-only audit script outside the build; neither is worth it for this closure. Revisit if the closure grows, and at once if it gains a network or TLS dependency.

## What the local gate does not cover

The hook checks whatever host invokes it, which for the whole of 0.1.0's development was **one platform and one R version**: macOS arm64 (Darwin 25.4.0) on R 4.6.0. CRAN checks Windows, Linux and r-devel. That is still true of *the hook*, but the sentence that used to follow it here — that the gap cannot be closed locally — was wrong, and `data-raw/check-matrix.sh` is what disproved it. What survives of the claim is Windows, which no local run reaches; `docs/win-builder.md` records the one manual win-builder submission that has ever checked it.

Qualifications, because the gap is narrower than "single platform" suggests and also wider in one specific place:

- **Narrower than it sounds for semantics.** The package's platform-varying behavior is already measured rather than assumed. The reality dialects model Apple's libc deliberately (architecture §3.1), and `data-raw/oracle-libc-linux.sh` runs the same oracles under glibc 2.36 and musl 1.2.5 with `tests/testthat/test-libc.R` asserting the divergence set (§3.3.0). So a cross-platform CI failure would be a build or check-mechanics failure, not a wrong address reading — the readings have three libcs behind them already.
- **The declared R floor is now measured, and it holds.** `DESCRIPTION` declares `Depends: R (>= 4.0.0)`, and `data-raw/check-r-floor.sh` runs `R CMD check --as-cran` against exactly that on x86_64 Linux: **Status OK, 0 errors, 0 warnings, 0 notes**, vignettes re-building and the full suite passing. The transcript is `docs/r-floor-check.md` (`RADD-dcquzofl`). The deleted GitHub workflow's `oldrel-1` and `oldrel-2` rows would only ever have probed *toward* the floor without reaching it, so that script — not any pipeline — is what stands behind the number, and losing those rows cost the claim nothing.
- **The gap that actually bit was dependency versions, not platform or R version.** Worth recording as its own axis, because nothing above covers it and it is where the one real correctness bug in 0.1.0 came from. The gate checks whatever *dependency versions* the host happens to have, which for the whole of 0.1.0 meant one set. `Imports: vctrs` carried no version floor, and vctrs < 0.7.0 modifies `vctrs_rcrd` types in place in `vec_assign()` — so `addr_reading(p, "curl")` silently corrupted the record, on every R version, for anyone holding the vctrs that was current on CRAN from 2023-12-02 to 2026-01-16 (`RADD-vppmbsia`, fixed by declaring `vctrs (>= 0.7.0)`). Two lessons stick. A dated snapshot pin freezes the *entire* closure, not just R, so a run that varies the pin is not varying one thing and cannot attribute a failure to R alone. And an unversioned `Imports:` entry is the same shape of unguarded claim as the R floor was: it asserts "any version works" and nothing checks it.

  **Both declared floors are now measured, and both hold.** `data-raw/check-dep-floor.sh` installs vctrs at **exactly** 0.7.0 — asserted with equality, not `>=`, because a `>=` assert is what left this gap standing while the existing floor script installed 0.7.2 and looked like a measurement — and runs the full check on R 4.0.0: **Status OK**, transcript at `docs/dep-floor-check.md` (`RADD-lfjdkynn`). It also closed the second half: vctrs 0.7.0 declares `rlang (>= 1.1.7)`, so raddr's rlang floor was real but *inherited* rather than stated, and `DESCRIPTION` now declares it. No unversioned `Imports:` entry remains. Two caveats travel with the run. It moves R and vctrs to their floors together, so a failure would not have attributed to either alone — the header carries a `BASE=` fallback that separates them, and it was not needed because the run passed. And a floor that holds today is not a floor that holds forever; this is a script to re-run when the floors move, not a result to cite indefinitely.

  **Since 2026-08-06 something other than memory notices when they move.** `data-raw/check-floor-drift.R` compares the floors `DESCRIPTION` declares against the floors the two transcripts recorded having measured, and against the numbers the two scripts pin — eleven comparisons over five files, no Docker, no network, ~0.3 s. `data-raw/verify.sh` runs it first in the chain, so the pre-push hook and `.gitlab-ci.yml` both carry it and a merge request cannot merge past it; a `.pre-commit-config.yaml` hook scoped to those five files also fires at commit time, where the answer is cheapest to act on. It re-measures nothing and cannot say a floor is *correct* — it says the transcript on disk was produced against the numbers now declared, which is the only part that was going unnoticed. `--self-test` mutates a throwaway copy and requires the guard to reject each mutation, because this tree is green by construction and eleven `ok` rows are also what a stuck script prints. Two of `RADD-olitgnsw`'s four triggers are now code (a raised floor, a new `Imports:` entry); the other two — a dependency release dropping R 4.0.0, and a CRAN resubmission — need the network or a person, so that issue stays open carrying them.
- **Three of the six CI rows are now measured locally, and Windows is the whole of what is left.** `data-raw/check-matrix.sh` runs macOS release on the host, Ubuntu release and Ubuntu r-devel in `rocker/r-ver` containers under amd64 emulation, and reports **Status: 1 NOTE on all three** — only the expected `--as-cran` incoming note. The transcript is `docs/check-matrix.md` (`RADD-kblrnovf`), and it accounts for every row: `oldrel-1` and `oldrel-2` are skipped deliberately because they probe toward a floor already measured, and `windows-latest` is **unreachable from this machine and checked by no automated gate** — `docs/win-builder.md` records the one manual win-builder run. Two cautions used to carry forward from that run, and both were settled on 2026-08-02 against native amd64 CI (`docs/gitlab-ci.md`), differently from each other. `libuv1-dev` is a **genuine system requirement**: the native devel job builds `fs` from source too and needs the same header package. The GNU tar 1.35 failure — which forced that run to copy the tree in with `cp` because tar cannot extract into a subdirectory under emulation — **does not exist off the emulator**, because a runner clones with git and never reaches `tar`. Both paragraphs stay in `docs/check-matrix.md` as written: they describe what that run experienced, and a transcript edited to reflect a later run is no longer a transcript. And neither container row pins a snapshot date, deliberately: pinning would move the dependency closure alongside the thing under test, which is the mistake recorded in the bullet above.
