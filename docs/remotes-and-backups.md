# Remotes, backups and mirrors

Demoted verbatim from `AGENTS.md` on 2026-09-05. Self-references such as "this file" and "this section" refer to the original.

`origin` is a **public** GitLab project (`gitlab.com/bart-turczynski/raddr`), reachable over SSH since 2026-08-01 and carrying every branch plus the annotated `v0.1.0` tag. It is the working remote, raddr's public identity, and since 2026-09-05 the **only** remote besides the local backup: the `github` remote was removed (`RADD-ithxwzpr`) rather than left in place returning 403, as it had since 2026-07-20. What this section used to say — that pushing is unavailable and the repository lives on one disk — is retired. An off-machine copy now exists that does not depend on remembering to move a file.

**It was private until 2026-08-13, and that is what blocked CRAN.** While private, an anonymous fetch returned 403 exactly as GitHub returns 404, so there was no address `DESCRIPTION` could name that a CRAN checker could reach. The owner flipped it to `visibility=public` with `issues_access_level=enabled` on 2026-08-13, and `URL:`/`BugReports:` were repointed off the dead GitHub account in the same change (`RADD-yrppvxdi`). Measured anonymously after the flip: the project root returns **200**, and `/-/issues` returns **404**.

**Superseded 2026-09-13: `BugReports:` names `/-/issues` again (`RADD-izuayetn`).** The `/-/work_items` repoint below drew the NOTE "The BugReports field in DESCRIPTION has .../-/work_items which should likely be .../-/issues instead" from R-devel's `tools:::.check_package_CRAN_incoming()`, and that NOTE got sibling pslr 1.2.1 archived at the CRAN pretest on 2026-09-12. The maintainer follows CRAN's suggestion: the `/-/issues` 404 to signed-out non-browser clients is accepted by CRAN (rurl 3.0.1 ships that form), and a browser is still redirected to `/-/work_items`. The two paragraphs below are kept as the record of what was believed when.

**Superseded 2026-09-11: `BugReports:` now names `/-/work_items`, and the 404 is gone.** This paragraph previously said the `/-/issues` 404 was expected and must not be "fixed". That guidance was wrong and CRAN acted on it: it archived `pslr 1.2.0` from incoming on 2026-09-11 citing exactly this URL as invalid. GitLab has migrated issues to work items and serves 404 on the legacy `/-/issues` path to any client that does not ask for HTML — which is how `R CMD check` resolves declared URLs (`curlGetHeaders()`, `Accept: */*`) — on every project, control-tested against `gitlab-org/gitlab`. A browser sends `Accept: text/html` and is redirected, which is why the link looked healthy by hand. The field is **repointed, not dropped**: `/-/work_items` returns 200 to the same anonymous checker. What remains is a *syntactic* NOTE — R expects a gitlab.com `BugReports:` path ending in `/issues` — and the replacement it suggests, `/-/work_items/issues`, returns 403, so it must not be adopted.

**Corrected 2026-09-10 — this was previously recorded as anti-scraping, and that was wrong.** Measured from one anonymous client in a single run, `/-/work_items` returns **200** for both `bart-turczynski/raddr` and `gitlab-org/gitlab`, while `/-/issues` returns 404 for both. Scripted clients are not blocked; the legacy path is. So the NOTE *is* fixable, by repointing `BugReports:` at `https://gitlab.com/bart-turczynski/raddr/-/work_items` — which is where issues are now filed, not a decoy 200. Do that in a release cycle, never inside a submission: it changes `DESCRIPTION`, which invalidates the tarball every recorded check row was measured against.

`DESCRIPTION` deliberately carries **no `https://CRAN.R-project.org/package=raddr` URL**, unlike rurl's and punycoder's. Those two are on CRAN; raddr is not yet (measured: that address 404s). Add it once raddr is accepted — adding it before would introduce exactly the kind of dead link this repoint removed, and a second NOTE that obscures the expected one.

Two local layers remain, following the convention used by sibling repos in `~/Projects/_backups/`:

- A `--mirror` clone at `~/Projects/_backups/raddr.git`, wired as the `backup` remote.
- Timestamped full bundles, `raddr_<branch>_<YYYYmmdd-HHMMSS>.bundle`, written with `git bundle create <path> --all` and checked with `git bundle verify`. A bundle is a single self-contained file holding every ref, so it stays the copy to hand to someone who can reach neither remote.

**Refresh the mirror with `sh data-raw/mirror-drain.sh`, not with `git push backup --all && git push backup --tags`.** That older command is what this section used to prescribe, and it adds and updates but never deletes. On 2026-08-01 the mirror was found carrying three heads with no local counterpart — `feature/ssrfr-api-seams`, `chore/hard-case-conformance`, `chore/peer-benchmarks` — every one an ancestor of `dev`. Nothing had been lost, which is precisely why nothing had noticed. The script prunes and then proves the result instead of assuming it, and it holds mirrors and working remotes to different standards on purpose: a mirror must match local exactly, while a working remote legitimately lags local by any branch not pushed yet (`RADD-vvdpvysm`).

Do not give `origin` a second push URL to fan out to several remotes on one `git push`. Git runs the pre-push hook **once per push URL** — measured with a two-URL remote and a counting hook, not assumed — so a fan-out runs the full `--as-cran` gate once per target. Mirror traffic goes through the script's `--no-verify` path instead, which is also right on the merits: those commits passed the gate already on their way to `origin`.

## The tracker is not in git unless it is snapshotted

`.fp/` is gitignored, so no commit, bundle or clone contains the issue tracker — while the tree cites `RADD-*` ids as the evidence behind its decisions. Run `sh data-raw/snapshot-tracker.sh` to regenerate `docs/tracker-snapshot.md`, which is the only copy of that reasoning in git. Refresh it before taking a bundle you intend to keep. `fp` stays authoritative; the snapshot is a backstop, and it is overwritten wholesale on every run.

`AGENTS.md` used to name `docs/architecture.md` as the thing doing the citing, which undersold the surface by enough to misprice the risk. Re-measured 2026-09-05 after this file was split out of `AGENTS.md`, over every tracked file rather than a hand-listed set: **63 distinct ids are cited outside the snapshot, and all 63 resolve inside it** — zero dangling references, against 155 issues in the snapshot. The figure recorded here earlier the same day was 60 and did not reproduce; the 2026-08-02 figure was 54 and had already drifted to 56 before that. Nobody edited any of those numbers — which is the ordinary way for a count in prose to go quietly wrong, and the reason this paragraph ends by telling you to re-run it rather than cite it. They appear in three files under `R/`, eleven under `tests/testthat/`, nine under `data-raw/`, nine under `docs/`, six under `bench/`, six under `docs/upstream-reports/`, one under `docs/research/`, and `.gitlab-ci.yml` and `.pre-commit-config.yaml` at the root. The 2026-08-01 figure of 51 was taken over a narrower sweep that missed `data-raw/` and the upstream reports entirely, which is worth noting because it undersold the surface in exactly the way this paragraph was written to stop. So losing `.fp/` without a current snapshot would strand a comment in shipped source and the provenance of every transcript, not one architecture document. Re-run that count rather than trusting this one if the tree has moved much: `comm -23` of the ids cited outside the file against the ids inside it should stay empty. Feed the file list on stdin rather than with `xargs -a`, which macOS `xargs` does not have — it fails silently under `2>/dev/null` and reports a count of zero, which reads exactly like a clean tree.

One consequence is not fixed by refreshing the snapshot. `.Rbuildignore` excludes `^docs$`, so the snapshot does not ship while `R/parse.R` does — a reader of the CRAN tarball meets `RADD-vppmbsia` at `R/parse.R:343` with nothing to resolve it against, and, when that sentence was written, could not reach the repository either. That half is now false — the GitLab project has been public since 2026-08-13 and `DESCRIPTION` names it — but the conclusion survives on its own merits: a tarball reader should not have to make a network request to understand a comment. Comments in shipped source should therefore be self-contained, carrying the id as a back-reference rather than as the explanation (`RADD-lfjdkynn`).
