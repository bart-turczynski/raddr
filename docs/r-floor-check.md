# R 4.0.0 floor check — transcript

Generated by `sh data-raw/check-r-floor.sh` on 2026-07-31. **Status: OK — 0 errors, 0
warnings, 0 notes.** `Depends: R (>= 4.0.0)` is now a measurement rather than a
declaration, and it holds. Vignettes re-build, the full suite passes, and `--as-cran`
is clean on x86_64 Linux under R 4.0.0.

This transcript **supersedes an earlier one from the same day** that reported 1 ERROR
and 7 test failures. None of those seven were R 4.0 findings, and the correction is
worth stating plainly because the first run's conclusion was wrong rather than merely
incomplete:

- **Six** were `RADD-vppmbsia`. vctrs < 0.7.0 modifies `vctrs_rcrd` types in place in
  `vec_assign()` instead of returning a copy, so resolving the `curl` composition
  blanked the record's own stored `aton` reading and corrupted it for every later read.
  `raddr_address` is a `vctrs_rcrd`. That bug is real, it was latent on **every** R
  version, and `DESCRIPTION` now declares `vctrs (>= 0.7.0)` against it.
- **One** was `expect_gt()` on two ISO-8601 date *strings*. testthat < 3.3.0 built its
  failure message with `act$val - exp$val` and forced it even when the expectation
  passed, so it always raised `non-numeric argument to binary operator`. The comparison
  itself was correct; only the formatting failed. Now compared as `Date`.

Both were **dependency-version artifacts, not R-version findings**, and both were
dragged in by pinning the whole closure to one snapshot date: a PPM snapshot freezes
every package, not just R, and vctrs 0.6.5 was current CRAN from 2023-12-02 to
2026-01-16 — the entire development span of 0.1.0. That is why this script now resolves
the closure and `rlang`/`vctrs` from two different dates, and asserts the vctrs version
it ended up with rather than trusting it. See the header of
`data-raw/check-r-floor.sh`.

The superseded transcript is in git history at `e7284f8`, and the reasoning that
followed from it is in `RADD-dcquzofl` and `RADD-vppmbsia`.
