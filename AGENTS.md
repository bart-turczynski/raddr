# Agent Instructions

Use committed docs for durable project knowledge. Keep raw planning notes, temporary context, and generated scratch work in `_scratch/`.

Do not commit `_scratch/`, `.fp/`, secrets, dependencies, build outputs, or local caches.

## Git hygiene

This project uses the [pre-commit](https://pre-commit.com) framework. Its config (`.pre-commit-config.yaml`) is cloned with the repo; each clone enables the hooks once:

```bash
pre-commit install && pre-commit install --hook-type pre-push
```

`pre-commit` is a Python tool. For non-Python templates, install it with `uv tool install pre-commit` or `pipx install pre-commit`.

### Per-commit checks

On every commit, lightweight hooks run: end-of-file fixer, trailing-whitespace trimming, merge-conflict detection, YAML/TOML validation, mixed-line-ending and case-conflict guards, and `check-added-large-files` — a portable 5 MB size guard that blocks accidentally committing heavy blobs (a big blob bloats `.git` history even after deletion).

### Pre-push verify gate

On `git push`, the `verify` hook runs the project's verify command: `data-raw/check-floor-drift.R --self-test`, then `lintr::lint_package()`, then `spelling::spell_check_package()`, then `rcmdcheck::rcmdcheck(args = "--as-cran", error_on = "warning")`. Since 2026-08-02 that chain lives in **`data-raw/verify.sh`**, and the hook and `.gitlab-ci.yml` both invoke it — so "the hook runs the same chain as CI" is a fact about one file rather than a coincidence between hand-maintained copies that was about to become three (`RADD-fgciezpx`). The one deliberate difference is a `NO_MANUAL` knob: CI images carry no LaTeX toolchain and pass `--no-manual`, the hook does not, and `docs/ci-workflow-lint.md` is where that asymmetry was examined and found correct. Server-side branch protection was unavailable on the GitHub plan, which is why this local pre-push gate was built as the stand-in for it. It is no longer the only layer: since 2026-08-01 `main` is a protected branch on the GitLab remote — `allow_force_push=false`, push and merge restricted to Maintainers — so the guarantee the hook was approximating now also exists server-side, on the remote actually being pushed to. Since 2026-08-02 the release **tags** are protected too, `v*` with creation restricted to Maintainers, which closes the asymmetry that had `main` guarded while `v0.1.1` — by then the only thing claiming that version number (`RADD-xuqkzgdl`) — could still be moved or deleted by a push. The two are not redundant. Protection rejects a bad *push*; it has no opinion about whether the tree passes `--as-cran`.

**A third layer now holds exactly that opinion, and it is the remote's rather than the laptop's.** Measured 2026-08-02: the project carries `only_allow_merge_if_pipeline_succeeds=true` with `allow_merge_on_skipped_pipeline=false`, so a merge request cannot merge until its pipeline has passed — and that pipeline runs `data-raw/verify.sh`, the same chain the hook runs. The two settings are load-bearing together: without the second, a skipped pipeline would read as success. Neither can be skipped into a bypass here anyway, because `.gitlab-ci.yml`'s `workflow:` rules run unconditionally on `merge_request_event`. What actually gates is `check:linux-release`; `check:linux-devel` is `when: manual` with `allow_failure: true`, so a devel job nobody starts blocks nothing — by design, and worth knowing before reading a green MR as two-platform evidence. Demonstrated the same day by MRs !17 and !18, both of which sat unmerged until their pipeline went green.

The gate is on the **merge**, not on every route into a branch. `main` is protected; `dev` is not, so a direct push to `dev` still reaches it without an MR and is checked by the local hook alone. Nothing prevents that, and it is how `dev` was advanced before merge requests existed on this remote.

**CI now runs.** `.gitlab-ci.yml` was added on 2026-08-02 and went green the same day: two jobs on GitLab's shared **native** amd64 runners, `check:linux-release` (R 4.6.1, p3m binaries) and `check:linux-devel` (R-devel r90334, source builds), both reporting **`Status: 1 NOTE`** — the `--as-cran` incoming note and nothing else. `docs/gitlab-ci.md` is the transcript (`RADD-fgciezpx`). The sentence this paragraph used to carry — that the local hook "is not a stand-in for CI, it is the only gate there is" — is retired, and it was retired by evidence rather than by intent: the first pipeline **failed**, on a missing `libcurl4-openssl-dev` that no local row could have found, because `rcmdcheck` imports `curl` and `data-raw/check-matrix.sh` calls `R CMD check` directly and so never installs `rcmdcheck` at all.

Two jobs, not six rows, is deliberate. Five of the six GitHub rows are already answered by measurements in `docs/`; what CI adds is the four things a laptop cannot assert about itself — a clean clone, a clean package library, native amd64, and a result tied to a commit. It does **not** add Windows (still checked by nothing, `RADD-xxuzwmuj`), macOS beyond the hook (a self-hosted Mac runner is *rejected*, not pending), minimum dependency versions, or any semantic diversity the libc oracles do not already provide.

`.github/workflows/R-CMD-check.yaml` mirrors the same chain across platforms. **It has still never run**, and a working GitLab pipeline does not change that: GitLab does not read `.github/workflows/`, so the workflow waits on the GitHub account and on nothing else. This file previously described the hook's chain as "the same chain CI runs" while no `.github/` directory existed at all; that sentence is now true, but it was made true by GitLab rather than by this workflow. It has been linted statically: actionlint 1.7.12 reports zero problems, and the three judgement calls actionlint cannot make — an `http-user-agent` key set on the r-devel matrix row only, `needs: lint` against a DESCRIPTION carrying no `Config/Needs` field, and `--no-manual` in CI but not in the hook — were each resolved against the `r-lib/actions` sources and found correct as written, with `docs/ci-workflow-lint.md` as the transcript (`RADD-ushiurrv`). That makes the file well-formed and its inputs understood; it does not make it exercised.

#### What the local gate does not cover

The hook checks whatever host invokes it, which for the whole of 0.1.0's development was **one platform and one R version**: macOS arm64 (Darwin 25.4.0) on R 4.6.0. CRAN checks Windows, Linux and r-devel. That is still true of *the hook*, but the sentence that used to follow it here — that the gap cannot be closed locally — was wrong, and `data-raw/check-matrix.sh` is what disproved it. What survives of the claim is Windows.

Qualifications, because the gap is narrower than "single platform" suggests and also wider in one specific place:

- **Narrower than it sounds for semantics.** The package's platform-varying behavior is already measured rather than assumed. The reality dialects model Apple's libc deliberately (architecture §3.1), and `data-raw/oracle-libc-linux.sh` runs the same oracles under glibc 2.36 and musl 1.2.5 with `tests/testthat/test-libc.R` asserting the divergence set (§3.3.0). So a cross-platform CI failure would be a build or check-mechanics failure, not a wrong address reading — the readings have three libcs behind them already.
- **The declared R floor is now measured, and it holds.** `DESCRIPTION` declares `Depends: R (>= 4.0.0)`, and `data-raw/check-r-floor.sh` runs `R CMD check --as-cran` against exactly that on x86_64 Linux: **Status OK, 0 errors, 0 warnings, 0 notes**, vignettes re-building and the full suite passing. The transcript is `docs/r-floor-check.md` (`RADD-dcquzofl`). The workflow's `oldrel-1` and `oldrel-2` entries still only probe toward the floor without reaching it, so that script — not CI — is what stands behind the number.
- **The gap that actually bit was dependency versions, not platform or R version.** Worth recording as its own axis, because nothing above covers it and it is where the one real correctness bug in 0.1.0 came from. The gate checks whatever *dependency versions* the host happens to have, which for the whole of 0.1.0 meant one set. `Imports: vctrs` carried no version floor, and vctrs < 0.7.0 modifies `vctrs_rcrd` types in place in `vec_assign()` — so `addr_reading(p, "curl")` silently corrupted the record, on every R version, for anyone holding the vctrs that was current on CRAN from 2023-12-02 to 2026-01-16 (`RADD-vppmbsia`, fixed by declaring `vctrs (>= 0.7.0)`). Two lessons stick. A dated snapshot pin freezes the *entire* closure, not just R, so a run that varies the pin is not varying one thing and cannot attribute a failure to R alone. And an unversioned `Imports:` entry is the same shape of unguarded claim as the R floor was: it asserts "any version works" and nothing checks it.

  **Both declared floors are now measured, and both hold.** `data-raw/check-dep-floor.sh` installs vctrs at **exactly** 0.7.0 — asserted with equality, not `>=`, because a `>=` assert is what left this gap standing while the existing floor script installed 0.7.2 and looked like a measurement — and runs the full check on R 4.0.0: **Status OK**, transcript at `docs/dep-floor-check.md` (`RADD-lfjdkynn`). It also closed the second half: vctrs 0.7.0 declares `rlang (>= 1.1.7)`, so raddr's rlang floor was real but *inherited* rather than stated, and `DESCRIPTION` now declares it. No unversioned `Imports:` entry remains. Two caveats travel with the run. It moves R and vctrs to their floors together, so a failure would not have attributed to either alone — the header carries a `BASE=` fallback that separates them, and it was not needed because the run passed. And a floor that holds today is not a floor that holds forever; this is a script to re-run when the floors move, not a result to cite indefinitely.

  **Since 2026-08-06 something other than memory notices when they move.** `data-raw/check-floor-drift.R` compares the floors `DESCRIPTION` declares against the floors the two transcripts recorded having measured, and against the numbers the two scripts pin — eleven comparisons over five files, no Docker, no network, ~0.3 s. `data-raw/verify.sh` runs it first in the chain, so the pre-push hook and `.gitlab-ci.yml` both carry it and a merge request cannot merge past it; a `.pre-commit-config.yaml` hook scoped to those five files also fires at commit time, where the answer is cheapest to act on. It re-measures nothing and cannot say a floor is *correct* — it says the transcript on disk was produced against the numbers now declared, which is the only part that was going unnoticed. `--self-test` mutates a throwaway copy and requires the guard to reject each mutation, because this tree is green by construction and eleven `ok` rows are also what a stuck script prints. Two of `RADD-olitgnsw`'s four triggers are now code (a raised floor, a new `Imports:` entry); the other two — a dependency release dropping R 4.0.0, and a CRAN resubmission — need the network or a person, so that issue stays open carrying them.
- **Three of the six CI rows are now measured locally, and Windows is the whole of what is left.** `data-raw/check-matrix.sh` runs macOS release on the host, Ubuntu release and Ubuntu r-devel in `rocker/r-ver` containers under amd64 emulation, and reports **Status: 1 NOTE on all three** — only the expected `--as-cran` incoming note. The transcript is `docs/check-matrix.md` (`RADD-kblrnovf`), and it accounts for every row: `oldrel-1` and `oldrel-2` are skipped deliberately because they probe toward a floor already measured, and `windows-latest` is **unreachable from this machine and checked by nothing**. Two cautions used to carry forward from that run, and both were settled on 2026-08-02 against native amd64 CI (`docs/gitlab-ci.md`), differently from each other. `libuv1-dev` is a **genuine system requirement**: the native devel job builds `fs` from source too and needs the same header package. The GNU tar 1.35 failure — which forced that run to copy the tree in with `cp` because tar cannot extract into a subdirectory under emulation — **does not exist off the emulator**, because a runner clones with git and never reaches `tar`. Both paragraphs stay in `docs/check-matrix.md` as written: they describe what that run experienced, and a transcript edited to reflect a later run is no longer a transcript. And neither container row pins a snapshot date, deliberately: pinning would move the dependency closure alongside the thing under test, which is the mistake recorded in the bullet above.

### Remotes, backups and mirrors

`origin` is a **private** GitLab project (`gitlab.com/bart-turczynski/raddr`), reachable over SSH since 2026-08-01 and carrying every branch plus the annotated `v0.1.0` tag. It is the working remote until further notice, and ultimately a pitch-perfect private mirror of GitHub once that account returns; `github` still returns 403 (suspended since 2026-07-20). What this section used to say — that pushing is unavailable and the repository lives on one disk — is retired. An off-machine copy now exists that does not depend on remembering to move a file.

Being private is deliberate and has one consequence worth keeping in view: it does **not** unblock CRAN. An anonymous fetch of the GitLab project returns 403 exactly as GitHub returns 404, so `DESCRIPTION`'s `URL` and `BugReports` stay pointed at GitHub and the submission blocker in `RADD-yrppvxdi` is untouched by any of this.

Two local layers remain, following the convention used by sibling repos in `~/Projects/_backups/`:

- A `--mirror` clone at `~/Projects/_backups/raddr.git`, wired as the `backup` remote.
- Timestamped full bundles, `raddr_<branch>_<YYYYmmdd-HHMMSS>.bundle`, written with `git bundle create <path> --all` and checked with `git bundle verify`. A bundle is a single self-contained file holding every ref, so it stays the copy to hand to someone who can reach neither remote.

**Refresh the mirror with `sh data-raw/mirror-drain.sh`, not with `git push backup --all && git push backup --tags`.** That older command is what this section used to prescribe, and it adds and updates but never deletes. On 2026-08-01 the mirror was found carrying three heads with no local counterpart — `feature/ssrfr-api-seams`, `chore/hard-case-conformance`, `chore/peer-benchmarks` — every one an ancestor of `dev`. Nothing had been lost, which is precisely why nothing had noticed. The script prunes and then proves the result instead of assuming it, and it holds mirrors and working remotes to different standards on purpose: a mirror must match local exactly, while a working remote legitimately lags local by any branch not pushed yet (`RADD-vvdpvysm`).

Do not give `origin` a second push URL to fan out to several remotes on one `git push`. Git runs the pre-push hook **once per push URL** — measured with a two-URL remote and a counting hook, not assumed — so a fan-out runs the full `--as-cran` gate once per target. Mirror traffic goes through the script's `--no-verify` path instead, which is also right on the merits: those commits passed the gate already on their way to `origin`.

### The tracker is not in git unless it is snapshotted

`.fp/` is gitignored, so no commit, bundle or clone contains the issue tracker — while the tree cites `RADD-*` ids as the evidence behind its decisions. Run `sh data-raw/snapshot-tracker.sh` to regenerate `docs/tracker-snapshot.md`, which is the only copy of that reasoning in git. Refresh it before taking a bundle you intend to keep. `fp` stays authoritative; the snapshot is a backstop, and it is overwritten wholesale on every run.

This file used to name `docs/architecture.md` as the thing doing the citing, which undersold the surface by enough to misprice the risk. Re-measured 2026-08-06, over every tracked file rather than a hand-listed set: **57 distinct ids are cited outside the snapshot, and all 57 resolve inside it** — zero dangling references. The 2026-08-02 figure recorded here was 54 and had already drifted to 56 before this measurement, without anyone editing the number — which is the ordinary way for a count in prose to go quietly wrong, and the reason the paragraph below tells you to re-run it rather than cite it. They appear in `R/parse.R`, eleven files under `tests/testthat/`, seven under `data-raw/`, six under `bench/`, six under `docs/upstream-reports/`, the measurement transcripts under `docs/`, and now `.gitlab-ci.yml` and `.pre-commit-config.yaml` as well. The 2026-08-01 figure of 51 was taken over a narrower sweep that missed `data-raw/` and the upstream reports entirely, which is worth noting because it undersold the surface in exactly the way this paragraph was written to stop. So losing `.fp/` without a current snapshot would strand a comment in shipped source and the provenance of every transcript, not one architecture document. Re-run that count rather than trusting this one if the tree has moved much: `comm -23` of the ids cited outside the file against the ids inside it should stay empty.

One consequence is not fixed by refreshing the snapshot. `.Rbuildignore` excludes `^docs$`, so the snapshot does not ship while `R/parse.R` does — a reader of the CRAN tarball meets `RADD-vppmbsia` at `R/parse.R:343` with nothing to resolve it against, and cannot reach the repository either while GitLab is private and GitHub 404s. Comments in shipped source should therefore be self-contained, carrying the id as a back-reference rather than as the explanation (`RADD-lfjdkynn`).
